## Fix: `null value in column "id" of relation "client_tasks"` on Add Client Task

### Root cause
`public.client_tasks.id` is `integer NOT NULL` with **no default and no attached sequence**:

```
column_default = NULL
pg_get_serial_sequence('public.client_tasks','id') = NULL
```

The frontend insert (`src/hooks/useStageTemplateContent.tsx:287`, `addClientTask`) intentionally omits `id` and expects the database to generate it. Because there is no sequence/identity, Postgres substitutes `NULL` and the NOT NULL constraint fires. Existing table already has 297 rows with `max(id) = 2479`, so this column was previously being populated by something upstream (legacy import) rather than by a sequence.

### Change (single migration, DB-only)
Attach an identity to `client_tasks.id` and seed it above the existing max so no future insert collides with legacy rows.

```sql
-- Convert client_tasks.id to a GENERATED BY DEFAULT AS IDENTITY column
-- and start the identity above the current MAX(id).
ALTER TABLE public.client_tasks
  ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY (RESTART WITH 2480);

NOTIFY pgrst, 'reload schema';
```

Notes:
- `GENERATED BY DEFAULT` (not `ALWAYS`) preserves the existing app pattern where callers may still pass an explicit id if needed (none currently do, but it's the safer choice for a table that was previously populated externally).
- `RESTART WITH 2480` = `MAX(id) + 1`, verified live. Guarantees the first auto-generated id will not collide with the 297 existing rows.
- No app code changes required — `addClientTask` already omits `id`.
- No RLS/grant changes; only the column default behaviour changes.

### Out of scope
- Sibling tables (`staff_tasks`, `emails`, `documents`) may have the same shape but the reported error is specifically `client_tasks`. Happy to audit them in a follow-up if you want.
- No frontend edits.
