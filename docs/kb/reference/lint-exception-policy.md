# Lint exception policy

Companion to the Phase 2.5 lint-debt retirement program in
[`codebase-optimization-plan-2026-08-28.md`](codebase-optimization-plan-2026-08-28.md#post-phase-2--lint-debt-retirement-planned).
Governs what may be excluded from the committed baseline
([`lint-baseline.json`](lint-baseline.json), generated by
`scripts/generate-lint-baseline.mjs`) and from later retirement-batch counts.

## What qualifies

Only these reasons justify an exception. "Large," "hard," or "not worth it
right now" are not exceptions — they're future batches, and stay in the
baseline so the program's totals don't quietly understate real debt.

- **Generated.** File content is produced by a tool, not hand-authored, so
  fixing a finding in it would be overwritten on the next regeneration (e.g.
  `src/integrations/supabase/types.ts` — Supabase CLI type generation).
- **External.** Vendored or third-party source checked into the repo verbatim,
  where changing it would diverge from upstream.
- **Runtime-boundary.** Code that only runs under a runtime this environment
  can't lint meaningfully against (e.g. Deno-only syntax/globals ESLint's
  TypeScript parser can't resolve locally) — distinct from ordinary
  `supabase/functions` code, which is in scope and counted normally.

## What does not qualify

- File size or finding count alone.
- "Nobody owns this code" — route it to an owner instead of excluding it.
- A rule the team disagrees with — change the rule in `eslint.config.js` and
  remeasure the baseline; don't carry a silent per-file exception for a
  repo-wide disagreement.

## Process

1. Add an entry to the `EXCEPTIONS` array in `scripts/generate-lint-baseline.mjs`
   with `path` and `reason`.
2. Add the same entry, plus who approved it and a reconsider-by date, to the
   table below.
3. Regenerate the baseline (`npm run lint:baseline`) and commit the updated
   `lint-baseline.json` alongside the policy change.
