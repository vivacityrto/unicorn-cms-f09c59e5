# To-Dos linked to Rocks and milestones

> **Last updated:** 2026-10-29 · **Reconsider by:** 2027-01-29 · **Confidence:** high on the database rules (run against `unicorn-qa` in a rolled-back transaction) and the logic (unit tests); medium on the screens (tests plus a browser walk of the new components with faked data, not the full panel on real data).
>
> **Status: built, in a pull request. The migration is applied to `unicorn-qa` and production (29 Oct 2026); the screens ship when the PR merges.**

## Why it exists

A milestone's Tasks box only ever held snapshots of GitHub issues, so a Rock whose work is not tracked in GitHub had nothing to show, and a standalone To-Do could not say which Rock it was for. The GitHub rows are static (the sync that kept them current was retired on 28 Oct 2026, see [rock-task-sync.md](rock-task-sync.md)). To-Dos are the app's own tasks (owner, due date, open or complete), so they can be linked, live, with no sync.

## What it is

- **A link from a To-Do to a Rock, or to one of that Rock's milestones.** A To-Do has at most one link ("it is for one thing"). Deleting a Rock, a milestone or the To-Do removes the link and never the other side: a To-Do whose Rock is deleted becomes standalone.
- **Rock side.** The Rock details panel shows **To-Dos for this Rock** (the Rock as a whole), and each expanded milestone shows its **To-Dos**: done count, overdue count, owner, due date, a tick box that marks the To-Do done or open again everywhere (the meeting's To-Do list included), **Add a To-Do** (title and date, owned by you, attached to the meeting when you are in one), **Link an existing To-Do**, and a small x that removes only the link ("the To-Do itself stays"). The milestone row's task figure counts these To-Dos with any linked tasks, shows "n overdue", and an open milestone with an overdue To-Do goes on the attention list. The same milestone **Linked tasks** box still shows the old GitHub rows, now labelled "snapshot as of <date>".
- **To-Do side.** On the meeting's To-Do list and the To-Dos page, each To-Do shows the Rock (and milestone) it is for, and staff get a **Link to a Rock** / **Change** control: pick a Rock (newest quarter first), optionally one of its milestones, Save; or **Make it standalone**. Linking a To-Do that is already linked moves it.
- **Discuss view.** A Rock with overdue To-Dos linked to it (itself or any milestone) shows "n To-Dos linked to it are overdue" in its flags and joins **Needs the room**. The deck is fixed when the view opens, so the filter picks the flag up as soon as the data arrives or when the filter is switched.

**The milestone row's last column (fixed 17 Nov 2026).** On a Team or Company Rock the column showed the Delivery figure even when nothing delivered the milestone, so a signed-off Team milestone with a completed To-Do read "0/0 done" and the To-Do count never appeared. The row now shows Delivery only when at least one milestone is delivering it; otherwise it shows the milestone's own To-Do figure, and "Nothing delivering" appears only when there is no To-Do progress to show (the warning stays in the details and on the attention list). The details no longer show an empty "Delivery · 0 of 0 done" block. Code: `MilestoneTable.tsx`; tests: `src/test/eos/milestone-table-task-column.test.tsx`.

Progress never completes a milestone: "ready for review" is only a hint and a person decides, using the **Sign off** button on the milestone row (see [rock-task-sync.md](rock-task-sync.md#signing-off-a-milestone)).

## Past To-Dos in the meeting's To-Do list

The live To-Do List segment shows this meeting's To-Dos (any status) plus every still-open To-Do carried over from earlier meetings, so a finished To-Do vanished from view as soon as its meeting was over. A **Show past To-Dos (completed and cancelled)** button under the list now opens a read-only list of the tenant's completed and cancelled To-Dos from earlier meetings, newest first (up to 150, with a search box once there are more than five), each showing when it was completed or cancelled, the owner, the IDS issue it came from and the Rock it is linked to (changeable). Nothing in it changes by clicking a row: a past To-Do is put back to Open only with its **Reopen** button, after which it joins the list to review. There is no "archived" state on a To-Do; completed and cancelled are the past states. Code: `usePastTodos` in `src/hooks/useMeetingTodos.tsx`, `src/components/eos/PastTodosPanel.tsx`.

**Undo.** A row in the meeting's live To-Do list toggles done on a single click, which made slips easy (a To-Do was marked done by mistake on 29 Oct 2026). Marking a To-Do done or not done now shows "Marked done" / "Marked not done" with an **Undo** button for 8 seconds. Undo puts back exactly what was there before (status and original completion time), is an ordinary second save (nothing depends on the toast staying open), and says "Undone" only if it worked. The generic "To-do updated successfully" toast is skipped for this path (`quiet` on `updateTodo`). If someone else changes the same To-Do in those seconds, Undo still sets it back (last save wins). Code: `src/hooks/useTodoToggleWithUndo.tsx`.

## Rock-level roll-up and status lines (17 Nov 2026)

The Rock details panel shows a **Rock work** strip above the milestones: one To-Dos figure for the whole Rock ("33 of 36 done", an overdue count and a thin bar), counting the Rock's own To-Dos and its milestones' together, once each, cancelled ones left out. The milestone summary figures are unchanged (milestone-level To-Dos only). Under the figure, a line appears wherever the status someone set disagrees with the To-Dos. The status stays a person's call; nothing here changes it or completes a Rock. The lines are deliberately narrow:

- **Complete, but linked To-Dos are still open** (with how many are overdue).
- **On Track, but linked To-Dos are overdue.** At Risk, Off Track and Blocked already say so, so they get no line.
- **No milestones, every linked To-Do done, Rock not Complete or Blocked:** "If the work is finished, mark the Rock Complete", with a **Mark Rock Complete** button for people who can change the Rock's status (the same write the milestone mismatch banner uses).

Not flagged on purpose: a Complete Rock with no milestones and no To-Dos. Production on 17 Nov 2026 had 21 of 46 Complete Individual Rocks in that state, so a line would be noise. Milestone progress against status keeps its own banner, unchanged. Lines wait until both the To-Dos and the milestones have loaded (and the milestone load has not failed), so a Rock is never flagged against an empty list or offered "mark Complete" while its milestones are unknown. Code: `src/utils/rockWork.ts` (rules and counts), `src/components/eos/rocks/detail/RockWorkStrip.tsx`, wired in `RockDetailSheet.tsx`; tests `src/utils/rockWork.test.ts`, `src/test/eos/rock-work-strip.test.tsx`. No schema, RLS or Edge Function change.

**On the Rock cards and the Discuss slide (17 Nov 2026).** Both show the same To-Dos line (done of total, overdue count, thin bar) and the same status lines, read-only (the Mark Rock Complete button stays in the Rock panel). The Rocks page fetches the figure for every Rock of the quarter in one batched call (`useRockTodoSummaries`, in chunks of 80, two kinds of query for the whole page, never one per card); it follows the quarter, not the search box, filters or tabs. A card shows nothing until the figure has loaded, and nothing if the fetch fails. On a card, the status lines also wait for the page's milestone figure (a card's milestone count only exists once that query has loaded), so a card is never flagged or asked "is the work finished?" while its milestones are unknown or failed to load; milestones kept on the Rock itself (older Rocks) count as milestones, as in the panel. On the Discuss slide the "On Track, but To-Dos are overdue" line is left out because the slide's flags already say "n To-Dos linked to it are overdue". The compact card layout is unchanged (no line). Code: `src/components/eos/rocks/RockWorkLine.tsx`, `RockCard.tsx`, `pages/EosRocks.tsx`, `RockDiscussSlide.tsx`, `useRockTodoSummaries` in `src/hooks/useRockTodos.ts`; tests `src/test/eos/rock-card-todo-work.test.tsx`, the "To-Do roll-up" block in `rock-discuss-dialog.test.tsx`, `todoSummariesByRock` in `rockWork.test.ts`. The figure refreshes when a To-Do or link is changed from the Rock panel; ticking a To-Do in the meeting's own To-Do list does not refresh it until the page refetches, the same as the Rock panel's figure.

## Rules worth knowing

- Writes to the link table go only through the three functions. Marking a To-Do done uses the same direct update the To-Do list already uses, so the existing To-Do rules apply (including the protection for To-Dos of a completed meeting).
- A To-Do made inside a meeting lands in that meeting's tenant, like the meeting's own To-Dos; otherwise in the Rock's tenant. A To-Do may belong to a different tenant than its Rock (staff work across tenants), which is why reading a link follows the Rock's rules and reading the To-Do follows the To-Do's.
- The same title added for the same target by the same person within 30 seconds is not added twice.
