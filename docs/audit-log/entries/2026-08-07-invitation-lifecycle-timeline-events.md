# Audit: 2026-08-07 — User invitation lifecycle (sent/resent/clicked/bounced/verified) wired into the client Timeline

**Trigger:** ad-hoc — Carl asked for Manage Invites status updates (invited, pending, clicked, bounced, verified) to be logged on the client Timeline, having noticed no invitation activity appeared there at all. Hand-applied hotfix branch (not routed through Lovable), audit entry required per `AGENTS.md → Schema / RLS / trigger changes` regardless of route.
**Scope:** `public.user_invitations` write paths (insert, resend, Mailgun webhook delivery/engagement updates, acceptance) and their (lack of) connection to `client_timeline_events`. Did not touch `cancel-invite` (`status='revoked'`) or the expiry paths (`status='expired'`) — see Open questions.

## Findings
- Confirmed live: **zero** `client_timeline_events` rows of `entity_type = 'user_invitation'` existed despite 226 real invitations in `public.user_invitations` (110 accepted, 9 clicked, 3 bounced/failed/complained, 214 sent at least once). The Manage Invites page (`src/pages/ManageInvites.tsx`) tracks this entire lifecycle already — it just never reached the Timeline.
- Click and bounce tracking are **not new infrastructure** — they already exist and are live: `supabase/functions/mailgun-webhook/index.ts` (public, HMAC-verified) writes `delivery_status` (`delivered`/`bounced`/`failed`/`complained`) and engagement columns (`first_opened_at`/`open_count`, `first_clicked_at`/`click_count`) on every real Mailgun event; `reconcile-invite-delivery-status` is a polling fallback for missed webhooks. This was a "wire existing data into triggers" task, not a "build new tracking" task.
- Every status-changing write is a plain SQL statement against one table (`invite-user`'s INSERT, `mailgun-webhook`'s two UPDATE branches, `resend-invite`'s UPDATE, `accept_invitation_v2`'s UPDATE), so a single set of triggers on `public.user_invitations` catches all of them centrally — no edge function changes needed.
- Did not reuse the existing `account_invited`/`account_activated` event types for this. Checked their only live writers first: `account_invited` is written solely by `bulk-account-actions`' ghost-user ("ghost" = a `users` row with no auth account) ***activation*** flow, and `account_activated`/`account_deactivated` are written solely by `rpc_set_client_account_status` toggling an *existing* account's `disabled` flag — a different meaning (enabling/disabling an account) from "someone completed self-service signup via an emailed invite link." Reusing them here would have conflated two unrelated flows under the same event type.
- "Pending" from Carl's ask was deliberately not made its own event type — it's the resting state between `invitation_sent` and one of the other three outcomes (clicked/bounced/accepted), not a transition of its own. Flagged this interpretation rather than silently dropping it.

## Code changes
- New migration `20260807060000_user_invitation_timeline_events.sql`:
  - Four new event types: `invitation_sent`, `invitation_clicked`, `invitation_bounced`, `invitation_accepted`.
  - `fn_invitation_sent_timeline_trigger()` — one function backing two triggers: `trg_invitation_sent_timeline` (`AFTER INSERT`) for the initial send, and `trg_invitation_resent_timeline` (`AFTER UPDATE OF last_sent_at WHEN OLD.last_sent_at IS NOT NULL AND changed`) for resends via `resend-invite`. Both write the same `invitation_sent` event type, titled "sent" vs "resent"; distinguished internally via `TG_OP` so the *first* `last_sent_at` stamp (which `send-invitation-email` also sets on the initial send) doesn't double-fire alongside the INSERT trigger — the resend trigger's `WHEN` clause requires `OLD.last_sent_at` to already be non-null.
  - `fn_invitation_clicked_timeline_trigger()` — `trg_invitation_clicked_timeline`, fires once on `first_clicked_at` going from null to set (not on every `click_count` increment, to avoid spamming the Timeline per click).
  - `fn_invitation_bounced_timeline_trigger()` — `trg_invitation_bounced_timeline`, fires on `delivery_status` transitioning to any of `bounced`/`failed`/`complained` (the full Mailgun terminal-failure spectrum, not just literal "bounced" — title names the actual outcome).
  - `fn_invitation_accepted_timeline_trigger()` — `trg_invitation_accepted_timeline`, fires when `status` transitions to `accepted` (title says "verified their account," matching the Manage Invites UI's own relabeling of `accepted` → "Verified").
  - All four functions `SECURITY DEFINER`, `SET search_path = ''`, `client_id = tenant_id::text` (matching the `rpc_set_client_account_status` precedent — `user_invitations` has no separate `client_id` column, tenant *is* the client here), default `visibility='internal'` (not client-visible), `entity_type='user_invitation'`, `entity_id = id::text`.
  - Backfilled full history (226 rows total: 226 `invitation_sent`, 9 `invitation_clicked`, 3 `invitation_bounced`, 110 `invitation_accepted`) — small enough for a full backfill (precedent: 113-row `time_reallocated` backfill). Historical resends aren't reconstructable (no log of past `last_sent_at` values), so only the original send is backfilled per row; resends only start being tracked going forward.
  - Dry-run tested inside a rolled-back transaction (`BEGIN ... ROLLBACK`) before applying for real — confirmed correct row counts and no syntax errors first.
  - Applied directly to prod Supabase after Carl's explicit `AskUserQuestion` approval; verified post-apply via `pg_trigger.tgenabled = 'O'` for all 5 triggers, live row counts matching the dry run exactly, and a live Playwright check against tenant 6277 (MCC Adelaide) showing both "Invitation sent to david.jamil@mcclabel.com" and "david.jamil@mcclabel.com verified their account" rendering correctly on the real client Timeline (correct icon/colour, "Accounts" filter chip, "View account" deep link, invited-by/accepted-by attribution resolving to real staff/client names).
- `src/types/timeline.ts`: added the four new event types to `TIMELINE_EVENT_TYPES`.
- `TimelineEventCard.tsx`: added the four types to the exhaustive `EVENT_ICON_MAP` (`UserPlus`/`MousePointerClick`/`AlertTriangle`/`UserCheck`) and `EVENT_COLOR_MAP`; extended `getModuleChip()`'s `account`-prefix check to also match `invitation`-prefixed types (both group under the existing "Accounts" chip rather than a new category); extended `getPrimaryAction()`'s account-events case to include all four, linking to `/tenant/{id}?tab=users` like the existing account events.
- `useClientManagementData.tsx`: added the four types to `EVENT_TYPE_FILTERS.accounts`, so they're included wherever the existing "Accounts" filter chip is used — no new filter chip needed.
- `npx tsc --noEmit` clean after all frontend changes (the icon/colour maps are `Record<TimelineEventType, ...>` — a missing key is a compile error, so this was a correctness check, not just a lint pass).

## Decisions
- Carl approved applying the migration directly to prod via `AskUserQuestion` after a clean dry run (`BEGIN...ROLLBACK`) showed the exact expected backfill counts with no errors.
- New event types rather than reusing `account_invited`/`account_activated` — a deliberate call to avoid conflating the ghost-user bulk-activation flow and the account-enable/disable toggle with the self-service email-invite lifecycle, even though it means four more entries in an already-large `timeline_valid_event_type` CHECK constraint and three more `Record<TimelineEventType,...>` map entries.
- Grouped the new types under the existing "Accounts" filter chip/category rather than adding a new "Invitations" chip — Manage Invites is conceptually about accounts, and this avoids further crowding an already-long filter bar (a UX complaint from earlier the same day, see `2026-08-07-portfolio-client-activity-feed.md`).

## Open questions parked
- `cancel-invite`'s `status='revoked'` transition has no Timeline event. Not requested (Carl's ask was invited/pending/clicked/bounced/verified only), but leaves a visible gap: a client's Timeline shows "Invitation sent" and then nothing if it's later cancelled, with no indication it was revoked. Worth asking whether a fifth `invitation_revoked` (or similar) event type should be added.
- Same gap for `status='expired'` (set by `accept_invitation_v2`'s expiry check and `check_invitation_expiry_trigger`) — invitations that simply time out unused leave no Timeline record either.
- `mailgun-webhook`'s `opened`/`first_opened_at` engagement signal (weaker than "clicked") was deliberately left off the Timeline — Carl's ask didn't mention "opened," and surfacing every email open felt noisier than useful. Worth confirming that's the right call.
- `supabase/functions/_shared/emit-timeline-event.ts`'s `VALID_EVENT_TYPES` Set (a second, independently-maintained copy of the event-type enum used by edge functions calling `emitTimelineEvent()` directly, as opposed to DB triggers) was already stale relative to the live DB CHECK constraint before this session (missing several event types added since `20260709232733`), and remains stale after this session too — not touched here since this feature is pure DB-trigger-driven and never calls `emitTimelineEvent()`, but it's real drift worth a cleanup pass on its own.
