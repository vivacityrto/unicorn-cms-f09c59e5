# Audit: 2026-08-07 — Manual/timer time-entry timeline coverage + missing "Time" filter chip

**Trigger:** ad-hoc — Carl asked whether client-logged time entries show up on the client Timeline; investigation found they largely don't, and Carl asked to fix it. Hand-applied hotfix (not routed through Lovable), audit entry required per `AGENTS.md → Schema / RLS / trigger changes` regardless of route.
**Scope:** `public.time_entries` write paths and their (lack of) connection to `client_timeline_events`. Did not touch the ClickUp sync pipeline or the `notes`-table timeline wiring (already correct, see Findings).

## Findings
- The Timeline already had `time_posted`/`time_ignored` as canonical event types (`src/types/timeline.ts`) with icon/colour mappings in `TimelineEventCard.tsx`, but the only trigger wiring them up (`fn_time_entry_timeline_trigger`, from `20260108050524`) fires on `public.calendar_time_drafts` `AFTER UPDATE OF status` — i.e. only time that originated as an auto-suggested Outlook/Teams meeting draft and was then posted/discarded by a user.
- Manually logged time (`AddTimeDialog.tsx`, the Client → Time tab's "Add Time" button) and the work-timer start/stop flow both insert directly into `public.time_entries` with no trigger back to the timeline at all. Confirmed live: **0** rows in `client_timeline_events` with `entity_type = 'time_entry'` despite 575 `source='manual'` and 6 `source='timer'` rows existing in `time_entries`.
- `time_entries.source` breakdown confirmed live: `clickup: 679, manual: 575, calendar: 10, system: 7, timer: 6`. Scoped the fix to `source IN ('manual', 'timer')` only:
  - `calendar` (draft-posted, via `rpc_post_time_draft`) is already covered by the existing `calendar_time_drafts` trigger — including it here would double-fire a `time_posted` event for the same logged time.
  - `system` (7 rows) are `RenewalConfirmDialog.tsx`'s negative-duration package renewal carry-over adjustments — an accounting entry, not a person logging work.
  - `clickup` (679 rows, `sync-clickup-time` / `ClickUpTimeTransfer.tsx`) is a bulk sync/import pipeline, not in-app manual logging. Deliberately left out — flagged as an open question below rather than silently included, since backfilling 679 rows across however many tenants without Carl's sign-off risked repeating the `public.notes` unscoped-backfill mistake from `2026-08-04`.
- Separately checked whether a note linked to a time entry (`AddTimeDialog.tsx`'s "link a note" flow, which inserts into `public.notes` with a `timeentry_id`) shows up on the Timeline — it does, via the existing `trg_notes_timeline` trigger (`structured_note_added`, fixed in the `2026-08-04` Phase-A-correction / PR #139). No change needed there. Noted but not fixed: that event's metadata carries the note text but not the linked time entry's duration/work type — cosmetic.
- Separately, the Timeline UI's filter chips (`FILTER_OPTIONS` in `ClientTimelineTab.tsx`) had no "Time" chip at all, even though `useClientManagementData.tsx`'s `EVENT_TYPE_FILTERS` already defined `time: ['time_posted', 'time_ignored']` — so even calendar-draft-sourced time events were only ever visible under "All", never filterable on their own. This predates this session; not clear when it was dropped.

## Code changes
- New migration `20260807010000_manual_time_entry_timeline_event.sql`: new trigger `trg_manual_time_entry_timeline` (`AFTER INSERT ON time_entries WHEN source IN ('manual','timer')`) → `fn_manual_time_entry_timeline_trigger()`, emitting an internal-only `time_posted` event per new manual/timer time entry. Backfilled the last 90 days (precedent: the `20260804070000` notes backfill's scoping rationale) — **377 rows**, all with `client_id` populated, confirmed via dry-run count before applying. Applied directly to prod Supabase; verified post-apply (`pg_trigger.tgenabled = 'O'`, backfilled row count matches, spot-checked row content/metadata).
- `ClientTimelineTab.tsx`: added the missing `{ value: 'time', label: 'Time', icon: Clock, staffOnly: true }` filter chip (internal-only, matching the trigger's default `visibility='internal'`).
- Did not add a live insert/delete round-trip test against the QA tenant (Test RTO A, 7517) as the `2026-08-04`/`2026-08-05` sessions did for their triggers — the harness's own permission layer denied both the `apply_migration` call and a follow-up test `INSERT` into `time_entries`, requiring Carl's explicit in-session approval before retrying `apply_migration` (granted) and blocking the test insert outright. Correctness of the INSERT path is evidenced instead by the 377-row backfill running the identical `INSERT ... SELECT` logic against real historical rows and producing correctly-shaped output on inspection.

## Decisions
- Carl explicitly approved applying this migration directly to prod (asked via `AskUserQuestion` after the harness blocked the first `apply_migration` attempt), choosing "apply now" over the offered alternatives (include ClickUp, trigger-only/no-backfill, or hold off).

## Open questions parked

- No live end-to-end insert test was performed against a QA tenant for the new trigger (see Code changes) — the backfill's output is the only production evidence the INSERT path is correct. Worth a manual "Add Time" smoke test on Test RTO A next time someone's in that flow.
- The `structured_note_added` event for a note linked to a time entry doesn't surface the time entry's duration/work type in its own metadata — cosmetic, not fixed this session.
