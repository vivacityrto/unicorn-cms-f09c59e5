# Audit: 2026-07-27 — csc-assignment-silent-failure

**Trigger:** drift-surfaced
**Scope:** Root-caused and fixed a frontend bug in the CSC (Client Success Champion) quick-reassign UI on the tenant/client detail page in `unicorn-cms-f09c59e5`. Did not audit the wider "CSC vs consultant assignment" split surfaced along the way — parked below, not actioned this session.

## Findings
- Carl reported that reassigning the CSC for a client ("Absolute Medic" / ABSOLUTE MEDICAL RESPONSE PTY LTD, tenant 7552) via the CSC dropdown on the client detail page "doesn't really change it."
- Root cause 1 (frontend, silent failure): `useTenantCSCAssignment.tsx`'s `assignCSC`/`removeCSC` mutations called `admin_set_tenant_csc_assignment` / `admin_remove_tenant_csc_assignment` via RPC and only checked the Postgrest transport-level `error`. Both RPCs reject invalid requests (caller isn't SuperAdmin, or the target user isn't flagged `is_csc`/`staff_team = 'client_success'`) by returning `jsonb_build_object('success', false, 'error', ...)` — a normal 200 response, no SQL exception. The mutation's `onSuccess` fired regardless: toast said "CSC Assigned"/"CSC Removed", the dialog closed, queries invalidated — but the `tenant_csc_assignments` row was never touched, so the refetch silently reverted to the previous CSC with no error surfaced anywhere. Same soft-fail contract exists on both RPCs (confirmed in migrations `20260702031811_958ec350-e0c6-4e84-b15b-0b0719023b0f.sql` for assign, `20260203064857_051c0830-b580-4e58-be18-e5fb999a48d1.sql` for remove) — a single shared bug in the frontend caller, not a per-RPC issue.
- Root cause 2 (database, real drift — investigated further this session, not just parked): `tenants.assigned_consultant_user_id` is a second, only partially-synced "who owns this client" column. `bulk_reassign_primary_csc` and `auto_assign_consultant` both keep it in sync with `tenant_csc_assignments`; `admin_set_tenant_csc_assignment` (the RPC behind the single-tenant quick-assign dropdown — the one in this bug report) never did. Confirmed via live `pg_get_viewdef`/frontend consumer sweep that `assigned_consultant_user_id` is the **sole** source for: `v_dashboard_tenant_portfolio.assigned_csc_user_id` (feeds the Triage Dashboard's attention ranking and `v_dashboard_labour_efficiency`, both live at `/triage-dashboard`), `v_executive_client_health.owner_user_uuid` (feeds `v_executive_consultant_distribution` and the Executive Dashboard's client-health owner filter, both live), and `compute_consultant_current_load`/`compute_consultant_weekly_capacity` (the capacity/load figures shown directly in `TeamReassignmentPage.tsx`/`BulkReassignCscDialog.tsx`, the bulk reassignment tool itself). Queried production directly: 7 of 413 tenants had drifted (all active clients, all with a documented `tenant_csc_assignments` reassignment history via this path that `assigned_consultant_user_id` never reflected) — confirmed the specific reported case (tenant 7552: `tenant_csc_assignments` correctly showed Tanya Janklin as primary CSC per 3 reassignments 8–13 Jul, while `assigned_consultant_user_id` still pointed at Dave Richards, frozen from before that history).
- Two components that read `assigned_consultant_user_id` most directly (`ConsultantAssignmentCard.tsx`/`useConsultantAssignment.tsx`, and `PortfolioTable.tsx`/`usePortfolioCockpit.ts`) are not imported by any live page — orphaned/unreachable, not contributing to current user-visible drift, no action taken.
