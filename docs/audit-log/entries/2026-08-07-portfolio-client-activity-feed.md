# Audit: 2026-08-07 — Portfolio-wide "Client Activity" dashboard widget + feed page

**Trigger:** ad-hoc — Carl asked whether the per-client Timeline feature (`client_timeline_events`, extended earlier the same day/session with manual/timer/reallocated time coverage) could be surfaced on the main staff dashboard as a live, cross-client activity feed, with a "View all" link to a dedicated full page. Hand-applied feature (not routed through Lovable); audit entry written because it includes a schema-adjacent change (Realtime publication membership) per `AGENTS.md → Schema / RLS / trigger changes`.
**Scope:** New read-only surfaces on top of the existing `client_timeline_events` table. No new tables, no RLS changes, no new event types. Touches `MainDashboard.tsx`, adds `usePortfolioTimeline.tsx` and `ClientActivityFeed.tsx`, and one Realtime publication migration.

## Findings
- **Main dashboard identified**: `src/pages/MainDashboard.tsx`, route `/dashboard` — confirmed as the staff landing page (non-staff redirected to `/client/home`; it's also `ProtectedRoute`'s universal fallback). Its `Panel` component already supports a `footerHref` prop that renders a "View all →" button navigating via react-router — an exact fit for the ask, no new UI pattern needed.
- **RLS was already portfolio-wide for reads**: `client_timeline_events`'s SELECT policy (`client_timeline_events_vivacity_select`, from migration `20260710000744`, superseding an earlier tenant-scoped version) grants every Vivacity staff role (`Super Admin`, `Team Leader`, `Team Member`, `Integrator`, `BGT`, `CSC`, `CET`) unrestricted SELECT across *every* tenant — no new RPC or view needed to query cross-client. The existing per-client `rpc_search_timeline_events` RPC, however, hard-requires non-null `tenant_id`/`client_id` and can't be reused as-is for a portfolio feed, so the new hook queries the base table directly (same approach already used by `useRiskCommandCentre.ts` for `real_time_risk_alerts`).
- **Realtime reliability gap found and fixed for this table only**: several existing hooks (`useRiskCommandCentre.ts` confirmed directly; likely others) subscribe to `postgres_changes` on tables that were never added to the `supabase_realtime` publication — confirmed live via `pg_publication_tables` that only `public.user_notifications` was actually in the publication before this session. Those existing subscriptions silently never fire; this is a pre-existing latent bug elsewhere in the codebase, **not fixed here** (out of scope — only `client_timeline_events` was added to the publication, specifically so the new portfolio widget's subscription actually works rather than silently no-opping the same way).
- **Defensive design given that finding**: `usePortfolioTimeline` pairs the `postgres_changes` subscription with a 30-second `refetchInterval` safety net, so the new widget/page still update within ~30s even if a websocket drops, Realtime has an outage, or a future regression removes the table from the publication again — it doesn't silently go stale the way the other hooks' realtime-only approach can.
- **Pre-existing bug found and fixed while reusing `TimelineEventCard.tsx`**: `getPrimaryAction()`'s deep links for `sharepoint_*`, `message_sent`, `stage_status_changed`, and all `account_*` event types pointed at `/clients/${tenant_id}?tab=...` — `/clients/:id` has never been a registered route (confirmed via `App.tsx`; the real route is `/tenant/:tenantId`). These "View X" buttons inside the per-client Timeline tab have been dead links since whenever they were written. Fixed by correcting the base path to `/tenant/` (the tab query values themselves — `documents`, `messages`, `packages`, `users` — were already correct against `ClientDetail.tsx`'s actual tab list).

## Code changes
- New migration `20260807040000_enable_realtime_client_timeline_events.sql`: `ALTER PUBLICATION supabase_realtime ADD TABLE public.client_timeline_events`. No RLS change. Applied directly to prod with Carl's explicit approval (asked via `AskUserQuestion` since this is a separate migration from the same-session time-entry-timeline work); verified via `pg_publication_tables`.
- New hook `src/hooks/usePortfolioTimeline.tsx`: react-query-backed, queries `client_timeline_events` directly (no tenant filter, RLS scopes it), batch-resolves tenant names via a second `tenants` query (same two-query pattern already used by `MainDashboard.tsx`'s existing "Client Messages" panel), supports `limit`/`eventTypes`/`search`. Subscribes to `postgres_changes` INSERT + 30s poll (see Findings).
- `MainDashboard.tsx`: new `ClientActivityPanel` component (reuses the existing `Panel` wrapper, `footerHref="/client-activity"`), inserted into the centre column between "Client Messages" and "Rocks". Shows the 8 most recent cross-client events with icon, client name, relative timestamp, and title; click navigates to `/tenant/:id?tab=timeline`.
- New page `src/pages/ClientActivityFeed.tsx` at route `/client-activity` (registered in `App.tsx`, plain flat staff route — no `/admin/` prefix, so it inherits the default "must be Vivacity Team" gate matching the RLS scope above, rather than being further restricted to Super Admin only as `RiskCommandCentre.tsx` is for its portfolio-wide view). Reuses `FILTER_OPTIONS` (exported from `ClientTimelineTab.tsx`) and `EVENT_TYPE_FILTERS` (exported from `useClientManagementData.tsx`) for filter chips, plus a local `groupByDate` helper mirroring `ClientTimelineTab.tsx`'s date-grouping UI (Today/Yesterday/This week/Older). Search box, offset-based "Load more" pagination (30 per page).
- Exported `EVENT_ICON_MAP`/`EVENT_COLOR_MAP` from `TimelineEventCard.tsx` (previously module-private) so the new dashboard widget and feed page render identical icons/colours per event type without duplicating the ~45-entry map.

## Verification
- Live end-to-end walkthrough via Playwright against the local dev server, logged in as Carl (Super Admin): dashboard widget renders real cross-client data (confirmed rows from both same-session time-entry-timeline fixes — manual/timer "Time logged" entries and MCC Adelaide's "Time reallocated" entries — appearing correctly); "View all" navigates to `/client-activity`; the "Time" filter chip correctly narrows to only `time_posted`/`time_ignored`/`time_reallocated` events across all clients; clicking a row navigates to that client's own `/tenant/:id?tab=timeline` and the MCC Adelaide reallocation events render correctly there too (closing the loop against the same-session per-client fix). Zero console errors throughout.
- **Environment snag, not a code issue**: this repo's dev-server port is a genuinely contended shared resource — three stale/unrelated `npm run dev` processes from other sessions/worktrees (`unicorn-cms-pkg-filter` on 8080, an old `ask-viv-client-assistant` worktree and a bare checkout both contending for 8081) were already running, causing the first two Playwright attempts to silently hit the wrong server. Resolved by explicitly starting on a verified-free port (`vite --port 8090 --strictPort`) rather than trusting the default auto-increment. Left the other sessions' processes untouched (not mine to kill).
- A dev-server side effect (not a real code change) modified `supabase/functions/mcp/index.ts` — a Lovable MCP bundler step rewrote the file's import to an absolute local Windows path pointing into this worktree. Reverted via `git checkout --` before committing; flagged here in case this bundler re-triggers unexpectedly during normal Lovable-side builds.

## Decisions
- Carl approved the Realtime publication migration explicitly (`AskUserQuestion`, chose "apply now" over "skip — polling is enough").
- New page gated as a plain staff route (all `VIVACITY_STAFF_ROLES`) rather than Super-Admin-only, matching the DB RLS scope rather than `RiskCommandCentre.tsx`'s stricter precedent — a judgement call, not explicitly asked of Carl; flagged here in case he'd prefer it narrower.
