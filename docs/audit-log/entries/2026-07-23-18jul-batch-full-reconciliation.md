## Findings

### DB-migration PRs — audited via a dedicated Opus subagent, then independently spot-verified
- **#19 (RESTRICTIVE writes on `user_roles`/`role_permissions`)** — confirmed not deployed; confirmed zero real gap (live PERMISSIVE policies already gate INSERT/UPDATE/DELETE on `is_super_admin_safe`). Applied as pure defense-in-depth, no behavior change. Independently re-verified: predicate matches exactly.
- **#23 (RESTRICTIVE backstops on `broadcast_recipients`/`invitation_tokens`/`staff_engagements`/`engagement_exit_interviews`/`tenant_users`)** — confirmed disjoint from the earlier M2 fix; confirmed its one new PERMISSIVE policy (`linked_user_select_own_engagement`) duplicates an already-live policy (`linked_user_select_own_offboarding`) with identical predicate — harmless redundancy, kept verbatim rather than editing. Applied, zero behavior change.
- **#28 (revoke anon EXECUTE, 102 trigger-only functions)** — confirmed not deployed, all 102 still anon-executable pre-fix (including the previously-flagged standalone gap `set_user_organisation`, now closed as a side effect). Found a real content bug: 3 of the 102 function names (`audit_issue_changes`, `enforce_issue_meeting_rules`, `sync_user_type`) no longer exist live — confirmed via `pg_proc` — which would have aborted the whole transaction. Stripped to 99 functions, applied, independently verified `0` still anon-executable across all 99.
- **#38 (revoke anon EXECUTE, 49 more trigger-only functions)** — same shape as #28. Found the same class of bug: `sync_rock_owner_from_seat` no longer exists live. Stripped to 48, applied, verified `0` still anon-executable.
- **#29 (tighten cohort-send RLS to `admin.cohort.send`)** — initially left as an open product decision in the prior audit. Resolved this session: confirmed `admin.cohort.send` is currently `full` only for Super Admin (every other role `none`), confirmed every historical `cohort_send_jobs` row (7 total) was created by a Super Admin, and confirmed both `/admin/cohort-sender` routes are already `requireSuperAdmin`-gated at the frontend level — zero real behavioral impact. Applied.
- **#31 (restrict `users` UPDATE RLS to admin-only)** — the one requiring redesign, not straight application. PR #31's own migration comment claimed relevant app paths were "already gated to admin.team_users.manage," but tracing every real `.from('users').update(...)` call site in `src/` disproved this: three flows (CSC toggle in `TeamUsers.tsx`, colleague-disable in `StaffEngagementDetail.tsx`, client job_title/phone edit in `TenantUsersTab.tsx`) write directly via the broad `is_vivacity_team_safe`-gated `users_update_staff` policy through plain `ProtectedRoute` routes with no admin gate — applying #31 as written would have 403'd all three for non-Super-Admin staff. Redesigned: left `users_update_staff` unchanged, added a new RESTRICTIVE backstop (`users_staff_edit_scope_restrict`) permitting non-admin staff writes to a colleague's row only when limited to `is_csc`/`disabled`/`job_title`/`phone` (via a jsonb-diff helper function rather than an explicit column enumeration, so it stays correct as the schema evolves); everything else on that row now requires `admin.team_users.manage` or Super Admin. Self-edits are exempted (already governed by the pre-existing `users_update_own` + escalation backstop). Explicitly flagged to the user that this interim fix reduces but does not eliminate re-audit risk, since the base broad policy still exists and the underlying product question (should non-admins retain these 3 capabilities at all) remains unresolved — user chose the RLS-only interim fix over the larger edge-function-conversion option.
  - **Follow-up bug caught post-apply:** the new helper function `user_staff_safe_fields_only_changed` retained live `anon` EXECUTE despite an explicit `REVOKE ALL ... FROM PUBLIC` in the migration — this project has a default-privilege setup that grants `anon` EXECUTE directly on new functions (separate from the PUBLIC grant), the same class of issue as the `cron.job` platform-grant finding from the prior session, just via a different mechanism. Low severity (the RESTRICTIVE policy calling it only applies `TO authenticated`, so `anon` couldn't reach it through RLS), but closed with an explicit `REVOKE ... FROM anon` follow-up migration. Independently re-verified: `anon`=false, `authenticated`=true, `service_role`=true (harmless, already-trusted role).

Both "retire" PRs (#30, #32) verified at the deployed-code level to genuinely return their 410 stubs, not just by title. No action needed on any of the 6.

### Cross-cutting
- **`tga_scope_items_cross_tenant_select`** — Lovable's automated suggestion system surfaced this finding unprompted three separate times this session. Investigated properly on the third occurrence rather than parking again: the table has **zero rows** (confirmed via direct count), so there is no current data exposure regardless of policy. The specific proposed fix was also found to have two real bugs — it checked `users.global_role = 'SuperAdmin'` instead of the codebase's standard `is_super_admin_safe()` helper (which would have wrongly excluded 6 real Super Admins whose access relies on `unicorn_role`), and its proposed join table (`tga_links`, 3 rows) covers a small fraction of the tenants the actual current source-of-truth table (`tenant_rto_scope`, 62 tenants) covers. **Decision: left parked** — table is empty, zero urgency, and a corrected fix (a straight deny-all for `authenticated`, matching the existing convention for stale/service-role-only tables elsewhere in this codebase) is ready to apply whenever wanted.
