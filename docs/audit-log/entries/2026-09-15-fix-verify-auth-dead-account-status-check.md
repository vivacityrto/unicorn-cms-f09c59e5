# Audit: 2026-09-15 — `verifyAuth`'s account-status check was silently dead across 16 Edge Functions

**Trigger:** ad-hoc, surfaced while drafting the golden-matrix packet for `admin.vector.manage` as a candidate fifth RBAC v6 vertical slice — checking that row's Edge Functions led to reading `vector-search` (a related-but-separate read path), whose auth pattern (`verifyAuth` + `checkSuperAdmin`/`checkVivacityTeam`) turned out not to be the isolated case it first looked like.
**Scope:** `supabase/functions/_shared/auth-helpers.ts`'s `verifyAuth`, and `supabase/functions/_shared/ask-viv-access.ts`'s `validateClientAskVivAccess` — a second, independent copy of the identical defect. 16 Edge Functions import `verifyAuth`; of those, 10 have no other authorization backstop at all.

## Findings

- **`verifyAuth`'s "is the account active" check compared `profile.state` to the strings `'inactive'`/`'suspended'`.** `public.users.state` is a `bigint` column — unrelated numeric data, not an account-status field. A TypeScript string comparison against a bigint value can never be true, so this check has never once fired, for any account, since it was written. It is not a recent regression; there is no way to date when it stopped (or started never) working from the repo alone.
- **A second, independent copy of the identical bug exists in `ask-viv-access.ts`'s `validateClientAskVivAccess`** (the gate for client-tenant users using Ask Viv in client mode) — same `profile.state === 'inactive' || profile.state === 'suspended'` comparison, same dead-on-arrival result. Its own doc comment explicitly warned against a *different* bug ("UserProfile exposes `state`, not `status`") while missing that `state` itself was never the right field.
- **Corroborating evidence this has been silently live for a while:** `validateAskVivAccess`'s own code comment (internal-staff Ask Viv gate) states "no separate active-state check here — verifyAuth() already gates on profile.state... so a second check... was dead code" — i.e. a past reviewer/session already investigated this exact area and *believed* `verifyAuth`'s gate was real, and removed a redundant check on that mistaken belief. That reasoning was correct in spirit ("don't duplicate the gate") but built on a check that couldn't fire.
- **Blast radius:** 16 Edge Functions import `verifyAuth`. Of those, `tenant-lifecycle` and the three `vector-index-*` functions (`vector-index-rebuild`, `vector-index-remove`, `vector-index-update`) also call `requireCaller`/`requireCallerByUserId`, which routes through `check_permission` — itself fixed earlier today for the same class of gap (see `docs/audit-log/entries/2026-09-15-gate-permission-core-on-disabled-and-archived.md`) — so those four already had a real, working backstop. The remaining **10 functions rely solely on `verifyAuth` + `checkSuperAdmin`/`checkVivacityTeam`** (which only check `unicorn_role`, with no disabled/archived filter of their own) for their entire account-status gate: `ai-suggest-rock`, `ask-viv-assistant`, `ask-viv-assistant-client`, `compliance-assistant`, `extract-note-title`, `fetch-clickup-comments`, `help-center-chat`, `outlook-time-draft-worker`, `sync-clickup-time`, `tga-fetch-scope`.
- **Confirmed live, not theoretical:** 10 currently disabled-or-archived internal-staff (`is_vivacity_internal = true`) accounts exist today. Disabling/archiving a user never revokes their Supabase Auth session (the only path that flips `public.users.disabled`, `rpc_set_client_account_status`, never touches `auth.users` — see the linked sibling audit entry for the same finding in a different context) — so any of those 10 accounts' still-valid sessions would have retained full access to all 10 unprotected functions indefinitely, including AI-assistant tools, ClickUp/TGA integrations, and the outlook time-draft worker.

## Code changes (this entry accompanies them)

- `supabase/functions/_shared/auth-helpers.ts`: `verifyAuth`'s `SELECT` now includes `disabled, archived`; the account-status check now tests `profile.disabled || profile.archived` instead of the dead `profile.state` comparison. `UserProfile` gains `disabled: boolean | null` and `archived: boolean | null`. `state` itself is left in the interface/select unchanged (it may be genuine unrelated data some other code depends on) — only the broken use of it as an account-status signal is removed.
- `supabase/functions/_shared/ask-viv-access.ts`: `validateClientAskVivAccess`'s equivalent check fixed identically; its own and `validateAskVivAccess`'s doc comments updated to stop referencing the old (wrong) field, so a future reader isn't misled the way a past one apparently was.
- New test: `supabase/functions/_shared/auth-helpers.test.mjs` (no prior test existed for either file) — static source-pattern assertions (this repo's established pattern for Deno-only files, since Deno isn't available locally): confirms the new `disabled`/`archived` select and check are present, and explicitly asserts the old dead `profile.state === 'inactive'/'suspended'` comparison is gone from both files. Run via `npm run test:edge`; full suite re-run clean at 315/315 after this change.

## Decisions

- Fixed the shared helper (root cause) rather than patching each of the 10 unprotected functions individually with their own `check_permission` call — this closes the gap uniformly for all 16 current and any future `verifyAuth` consumer, and matches the existing precedent (`is_vivacity_team_safe`, now-fixed `has_permission`/`check_permission`) of the account-status check living in one shared place.
- **Not attempted here: deploying this fix.** Unlike this session's earlier SQL fixes (applied instantly via `apply_migration`), this is Edge Function *source* code — `auth-helpers.ts`/`ask-viv-access.ts` are bundled into each importing function at deploy time, so the fix only takes effect once every one of the 16 consumer functions is actually redeployed. Per `AGENTS.md`'s own standing caution ("Supabase's GitHub sync integration... has been observed to fail silently... do not merge an Edge Function PR into `main` without being ready for it to go live"), redeploying 16 functions is a larger, more visible production action than this session's single-function security fixes today and is being surfaced to Carl explicitly rather than actioned unilaterally.
- Did not add a `check_permission`-based backstop to the 10 unprotected functions in this same change — that would be a second, independent layer of defense-in-depth worth considering, but is a larger design decision (which feature key should gate each of these 10 functions?) outside this bounded fix's scope. Flagged as a follow-up.

## Verification

- `npm --test supabase/functions/_shared/auth-helpers.test.mjs` — 6/6 pass.
- `npm run test:edge` (full suite) — 315/315 pass, 0 failures, confirming no other function's behavior changed.
- Confirmed via `grep` that no other file in `src/`, `supabase/functions/`, or `scripts/` reads `profile.state` for an account-status purpose (the two fixed occurrences were the only ones).
- Did not attempt to reproduce the exploit live (would require signing in as one of the 10 real disabled/archived accounts against production); the source-level evidence (a string-vs-bigint comparison that can never be true, confirmed via `information_schema` that `state` is `bigint`) is conclusive on its own, the same standard used for the `upsert_rock_with_parenting` finding earlier today.
