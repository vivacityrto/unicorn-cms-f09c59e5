# Audit: 2026-08-06 — ask-viv-client-assistant

**Trigger:** ad-hoc
**Scope:** New sibling edge function (`ask-viv-assistant-client`), two schema migrations (foundation tables + `app_settings` rollout flags, then a token-usage-cap table), a frontend panel rewrite, and a same-day follow-up round (usage cap, invite-diagnosis tool, a data-accuracy correction, and two production bugs found during QA) in unicorn-cms-f09c59e5, replacing the client-portal Ask Viv assistant. Did not review any other schema areas.

## Findings
- Carl asked to bring the new agentic Ask Viv assistant (`ask-viv-assistant`, shipped for Vivacity staff only) to the client portal, plus a portal/Vivacity Academy navigation capability. Investigation found a client-facing Ask Viv already exists and is live today (`compliance-assistant-client` + `ClientAskVivPanel.tsx`, mounted on every `/client/*` route) — deterministic/template-based, phrased via Gemini through the Lovable AI Gateway, distinct architecture from the new staff assistant (direct-Anthropic Claude Sonnet, agentic tool-use).
- The frontend's `useRBAC.tsx` has a permission comment stating "Ask Viv is Vivacity-only — no client access under any circumstances." Confirmed this governs the *staff* assistant's `ask_viv:access` permission specifically, not the separate client-portal surface — left untouched.
- Carl confirmed the intent: **replace** the existing client assistant with a new tenant-locked sibling of the staff agentic assistant, rather than run both or bolt navigation help onto the old one. Standards/regulatory interpretation for clients — explicitly excluded in the original 30 Apr client-mode build spec (`docs/kb/handoffs/ask-viv-client-mode.md`) — stays excluded; reaffirmed rather than silently carried over.
- During design, found `client_timeline_events` already has a `visibility` column (`'internal'` default, `'client'` opt-in) with client-read RLS restricted to `visibility = 'client'` rows only (migrations `20260210071340`, `20260513025021`) — notes/documents wired into the timeline in early-August migrations do not set `visibility`, so they insert with the safe `'internal'` default and are invisible to client RLS by construction. This resolved an open design question about whether the new assistant's account-context tool could leak notes via the aggregated timeline feed: using the RLS-scoped (user-auth) Supabase client for this tool, rather than service-role, makes that leak structurally impossible regardless of application-layer filtering.
- Found the zero-arg `is_vivacity()` helper referenced in team conventions docs is not the current live staff-check function — it's `is_vivacity_team_safe(uuid)` (checks `users.is_vivacity_internal`, correctly excludes archived/disabled staff; see `20260731040112_revert_is_vivacity_staff_regression.sql`). Used the real function in the new RLS policies.
- Found `ask-viv-assistant` (staff) and its sibling ingestion functions are not registered in `supabase/config.toml` at all, unlike older functions — the newer convention in this repo appears to skip explicit config.toml entries. Followed that precedent; did not add an entry for `ask-viv-assistant-client`.
- **Post-deploy QA found two real production bugs, both fixed same-session:**
  1. `app_settings` has its own RLS restricting SELECT to staff (`is_super_admin_safe()` OR `is_vivacity_team_safe()`) — a client-tenant user querying it via the RLS-scoped client gets zero rows back unconditionally, so the rollout-flag check and (once added) the token-cap check always failed closed for real clients. Fixed by creating a `serviceClient` once in the request handler and using it specifically for `isClientAssistantEnabledForTenant` and `checkClientTokenUsageCap` (config/rollout-flag reads only, not tenant data — doesn't weaken the tenant-isolation architecture built around the user-auth client for everything else). A related but distinct bug in the same rollout-flag check — comparing a `bigint[]` beta-tenant-id column with `.includes(tenantId)`, which silently fails on a `"7547"` (string, as PostgREST can serialise bigint[] elements) vs `7547` (number) mismatch — was fixed alongside it via `.some((id) => Number(id) === tenantId)`.
  2. `get_my_account_context` called the shared `_shared/ask-viv-fact-builder` module (built for the staff assistant), whose `validateInput` unconditionally rejects any `role` that isn't a Vivacity-internal role — meaning it rejected every real client call (`unicorn_role` is `Admin`/`User` for clients, never a staff role), so this tool failed for every client, every time, pre-rollout-flag-fix. Fixed with a new optional `caller_role_class?: "staff" | "client"` field on the fact-builder's input type (`_shared/ask-viv-fact-builder/types.ts`) — `validateInput` (`validation.ts`) skips the internal-role check when it's `"client"`. The client function now always passes `caller_role_class: "client"`; the staff function passes nothing, so its behaviour is unchanged. Access control for the client path was already fully enforced upstream by `validateClientAskVivAccess` before this is ever called, so the internal-role check was redundant defense for that path, not a real gate being removed.
- **Data-accuracy correction (Carl-flagged):** the navigation manifest and `get_invite_status`'s guidance originally referenced an "Academy → Team Members" page (`/academy/team`) for inviting Academy-only learners, based on earlier research claiming it existed for Team/Elite tiers. Carl flagged this from memory ("I don't remember having team members anywhere"); live Playwright verification against the Demo RTO account confirmed the route renders but is wired to placeholder/mock data (fake names, `@example.com` emails) unconnected to the real tenant. Removed `/academy/team` from `ACADEMY_PAGES` entirely (with a code comment recording the finding and verification date) so `find_portal_page`/the assistant never recommends it; corrected all references to point to `/client/users` instead, which was independently verified live to show real tenant data and a real "Academy only" access-scope value.
- **Operational note, not a code finding:** partway through the same-day follow-up round, another AI coding tool (Cursor) checked out an unrelated branch (`hotfix/swap-primary-contact-timeline`, based on a commit before this feature existed) in this same shared working directory, for a different task. Because several of this round's edits (see Code changes below) were still uncommitted at that point, the checkout silently reverted them from disk back to that branch's pre-feature state — the prod edge function deployment itself was unaffected (each `deploy_edge_function` call sends its full file bundle inline, independent of local disk state), but the local working tree needed to be reconstructed. Recovered via a `git worktree` checked out to `feat/ask-viv-client-assistant`, isolated from the directory Cursor had checked out, so the two tools' work no longer collides. See `AGENTS.md → Concurrent agents in a shared working directory` for the standing guidance this prompted.

  - `supabase/functions/_shared/ask-viv-client-redaction.ts` (new) — deny-list/friendly-label logic extracted from `compliance-assistant-client/index.ts` so both the old and new client surfaces share one redaction definition during the transition.

## Decisions
- Confirmed with Carl: replace the client-portal Ask Viv outright (not dual-run), keep Standards/regulatory search excluded for clients, filter the account-context tool's timeline feed per-entry (resolved via RLS rather than app-layer logic, per the finding above).
- The Supabase MCP connection was not available at the start of this session (no `supabase` CLI installed either) — the migration and edge function were initially committed to the PR only. Carl connected the MCP mid-session and gave explicit approval to apply directly to prod; both the migration and the new function are now live (see Code changes above).
- Carl asked for a daily usage cap "stacked PR strat if you have to" — judged a stacked PR unnecessary and kept this all on `feat/ask-viv-client-assistant` instead, since it's the same feature surface.
- Carl asked for invite-status diagnosis to help clients self-serve on "why is the link invalid" questions, including inviting Academy-only learners and secondary contacts — see `get_invite_status` above.

## Open questions parked
- Whether `client_action_items` and `v_audit_schedule` (used by `list_my_deadlines`) already grant client-portal SELECT under RLS wasn't independently verified against a real client login this session — the existing client Tasks/Reports pages appear to depend on equivalent access, but this needs confirming during the manual QA pass (see plan's verification section) before rollout.
- Whether other client-facing tools share the `app_settings`-RLS or fact-builder-role-gate failure modes found here wasn't swept for elsewhere in the codebase — these two were found via this specific QA pass, not an exhaustive audit.
- Whether to eventually dual-write client Ask Viv interactions into `ai_interaction_logs` (for the shared AI Insights dashboard) was considered and deliberately deferred — the new `ask_viv_client_turns` table already serves as this surface's audit trail; folding it into the cross-surface dashboard is a separate scoping decision, not bundled into this change.
