# Audit: 2026-07-22 — git-drift-reconciliation

**Trigger:** drift-surfaced (follow-on from [[2026-07-22-tga-gate-and-blast-radius-fixes]], which left "the broader git-drift problem" explicitly parked)
**Scope:** Reconciled two distinct classes of git/production divergence from the 12–21 Jul security remediation window: (1) migrations applied live but never committed to git, and (2) the opposite — migrations merged to git but never deployed live, due to a broken `deploy-supabase.yml` CI step. Did not action: the CI fix itself (explicitly out of scope per user instruction), or a re-check of the ~17 remaining un-audited PRs from the 18 Jul stuck batch.

## Findings

### 14–16 Jul window — live but never committed (33 migrations total)
- Cross-referenced all `supabase_migrations.schema_migrations` versions from this window against `supabase/migrations/`. 1 was already covered under a different filename (byte-identical content, same-day timestamp offset). The remaining 27 were genuinely missing — spanning an entire undocumented "package-hours" refactor (`fn_package_used_minutes` + 8 dependent migrations), a full Assessment Validation Tool schema, and 15 individual security/bugfix migrations. All 27 backfilled verbatim into `supabase/migrations/`, verified content-exact against live `pg_get_functiondef`/`pg_policies`/`information_schema` state.
- One historical-accuracy note preserved deliberately: 3 of the 27 (`l3_gate_tga_sync_cluster`, part of `l3_gate_templates_packages_cluster`, part of `l3_gate_remaining_utility_functions`) were themselves later superseded by the 22 Jul TGA-gate fix from the companion session — backfilled as their original (buggy) content anyway, since that's the true bug-then-fix git history.

### 12–13 Jul window — not tracked in `schema_migrations` at all (6 findings)
- A separate, earlier security pass (12–13 Jul) left 6 findings with **zero** trace anywhere — not in git, not even in `schema_migrations`. All 6 confirmed live-current via direct DB inspection, then independently blast-radius-checked (every real frontend/edge-function caller traced) before backfilling:
  - **C2** — `users_no_privilege_escalation` RESTRICTIVE policy blocking self-escalation of `unicorn_role`/`tenant_id`/etc. via direct REST.
  - **H1** — drop of a stale world-readable `emails_authenticated_select` policy.
  - **H3** — internal-onboarding storage bucket read/update/delete scoped to `admin.team_users.manage:full` (upload path was separately, unrelatedly iterated on 3 times in git; read/update/delete had zero git trace).
  - **M2** — RESTRICTIVE backstops on 5 sensitive tables (`emails`, `auth_tokens`, `oauth_tokens`, `cohort_send_jobs`, `cohort_send_job_items`).
  - **M3** — anon EXECUTE revoke on admin/bulk functions. The historical "92 functions" figure could not be substantiated against live data; re-derived from `pg_proc`/`has_function_privilege` ground truth instead, yielding 15 functions (2 already covered by separate committed migrations, 4 confirmed to have zero callers anywhere in the codebase, `set_user_organisation` deliberately excluded — see below).
  - **L1/L3** — drop of a stale `_tenant_users_contact_backfill_20260512` table + `cron.job_run_details` SELECT revoke. (`cron.job` itself required separate handling — see next finding.)
  - All 6 applied live via `apply_migration` under fresh timestamps (rather than guessed historical dates, since no original `schema_migrations` record ever existed to anchor to) and independently re-verified post-apply against live DB state. Git sync initially stalled — the 6 files sat in Lovable's working tree but didn't reach `origin/main` for several hours despite no error on Lovable's side; resolved by Lovable appending a trailing comment to each file to force a fresh Lovable→GitHub sync event. Post-sync, all 6 confirmed present on `origin/main` with correct core SQL (spot-checked in full for all 6), and — as a side effect of the re-sync triggering a fresh `db push` — all 6 now also have proper `schema_migrations` records with `name` matching the git filename exactly, fully closing the tracking gap rather than leaving it partial.

### The opposite-direction problem — 18 Jul PRs merged to git, never deployed
- Discovered mid-session: an entire batch of ~19 PRs merged to `main` on 18 Jul (and after) never reached production, because `supabase db push` has been silently failing on every merge since (confirmed: zero `20260718*` versions in `schema_migrations`; edge functions deploy via a separate, unaffected path). Per explicit user instruction, the CI root cause itself was not investigated further — only the functional consequences.
- Of this batch, 2 items were deep-checked:
  1. `enforce_invitation_role_ceiling` — a real, live, currently-exploitable gap. Fixed; full detail in [[2026-07-22-invitation-role-ceiling-trigger]].
  2. `admin.broadcast.send` permission scope — investigated as an apparent divergence (live has Team Leader/Team Member at `full`, PR #25's committed version specifies `none`/omits Team Member entirely). **Correction made mid-investigation:** this is not unexplained drift — a second migration (`20260719034741_ab3fd366...sql`, committed 19 Jul, explicitly widening both roles to `full`) already exists in git and was never flagged before now. It was never applied via tracked tooling either, but its content matches live state exactly, meaning it's genuinely the same "authored, applied live via direct SQL, never tracked" pattern as everything else this session — not a mystery. **User decision: leave as-is** (Angela's change; both roles are functionally unused — Team Leader has zero users of any status, Team Member has 1 active of 7 total).
- **`cron.job` (PR #24/#36) — investigated, found to be a platform-level constraint, not fixable via project migration.** Original assessment (this session, before the correction below) incorrectly concluded `cron.job`'s live ACL already matched the target state, based on an `information_schema.role_table_grants` query. **This was wrong** — direct `pg_class.relacl` inspection shows PUBLIC genuinely still holds `SELECT`. A plain `REVOKE` (run outside any transaction/assertion, as a clean diagnostic) executed without error but had zero effect, because the grant was made by `supabase_admin` and the role migrations execute as (`postgres`) is not a superuser and isn't that grant's owner — Postgres silently no-ops a REVOKE the executing role lacks authority over. Ruled out the more serious hypothesis first (checked `pg_auth_members`: `anon`/`authenticated`/`service_role` have zero role memberships of any kind — this is not a cluster-wide inherited-privilege leak). Confirmed via a real PostgREST API call (`Accept-Profile: cron` → `406 PGRST106`) that the `cron` schema is not exposed to the REST API at all — `public` and `graphql_public` only — so this grant, while real at the raw ACL level, is unreachable by any actual application user; only a direct Postgres connection authenticated as `anon`/`authenticated` could exploit it, which no real user has. **User decision: leave as a documented, known, non-exploitable, platform-level gap** rather than open a Supabase support ticket.
